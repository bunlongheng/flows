Key decisions
Queue-first fan-out. Never send inline in the API request. Segmenter explodes a campaign into millions of small jobs; workers pull at whatever rate the MTA + ISPs tolerate. Backpressure = queue depth.
Sharded Postgres by subscriber_id hash. 500M rows is too much for one node; 8 shards keeps each ~60M and lets segmentation run in parallel per shard.
Suppression list is sacred. Every send checks a bloom-filter + DB of unsubscribes / hard bounces / complaints before handing to the MTA. Sending to these tanks your reputation and breaks the law (CAN-SPAM/GDPR).
At-least-once + idempotency key. Each job carries (campaign_id, subscriber_id); workers dedupe via a Redis SET so a retried job never double-sends.
DKIM / SPF / DMARC from day 1. Sign every message. Without auth, 500M messages go straight to spam and your domain gets blocklisted.
Where Tier 1 breaks (why you go to Tier 2)
▸ Single region = one datacenter outage stops all mail. No DR.
▸ Redis/SQS as the bus handles jobs but not analytics fan-out; every consumer that wants events (billing, dashboards, ML) hammers the same queue or DB.
▸ No per-ISP throttling. You blast Gmail/Yahoo at one flat rate → deferrals, throttling, reputation damage. Deliverability is left to luck.
▸ Analytics = batch on Postgres. "How's the campaign doing?" is a slow query, not real time.
▸ IP warm-up + reputation is manual. A bad campaign can blocklist a shared IP and hurt every customer.
Bottom line
Tier 1 delivers 500M emails reliably with a queue, a worker fleet, sharded Postgres, and disciplined suppression + DKIM. It's the right first system - simple, cheap, one team can operate it - but it's single-region, has no real-time analytics, and treats deliverability as luck. Good enough to launch; it will bottleneck on availability and ISP throttling.
